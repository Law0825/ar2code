# 代码实现

## 目标

按 `design.md` 的目标与围栏、`plan.md` 的依赖顺序、`task.md` 的变更单元和已通过的 DT 基线完成生产实现。

## 执行方法

### 1. 围栏配置读取与检查
在开始实现前，必须先读取并理解设计中的围栏配置：
- 从 `design.md` 读取"模块变更计划"部分
- 明确 ✅允许修改、❌禁止修改、🔵条件修改、📦新增的文件范围
- 将围栏配置保存到当前执行上下文中

### 2. 按步骤执行实现
1. 确认输入版本和 DT 质量评审为 `pass`；
2. 按 plan 波次和 task 依赖选择当前可执行任务；
3. 从任务声明的路径、符号和相邻实现模式读取必要代码；

### 3. 围栏校验（关键步骤）
在修改任何文件前，必须进行围栏校验：

**校验流程**：
1. 检查目标文件是否在 ✅允许修改 或 📦新增 列表中
2. 如果在 ❌禁止修改 列表中：
   - 立即停止当前操作
   - 记录越界尝试
   - 触发围栏突破流程
3. 如果在 🔵条件修改 列表中：
   - 检查修改是否满足条件
   - 不满足条件时：
     - 使用ACEHarness人工客服协议请求用户确认
     - 每轮一个请求，说明已知事实、待决策内容及其影响
     - 发出请求后停止当前步骤，等待用户回答
     - 恢复后先记录回答，再继续

**围栏突破流程**：
当必须修改禁止范围的文件时：

1. **暂停当前实现**，评估是否真的需要突破围栏

2. **确认突破必要性**：
   - 仅当缺口会改变接口、数据、权限、兼容性、异常行为、验收口径或测试断言时请求人工
   - 如果有其他方案避免修改禁止文件，优先尝试替代方案

3. **使用ACEHarness人工客服协议请求授权**：
   - 每轮一个请求，最多三个相关问题
   - 问题正文说明已知事实、待决策内容及其影响
   - 使用运行时支持的回答类型
   - 发出请求后停止当前步骤，等待用户回答

   **请求格式示例**：
   ```
   ## 围栏突破授权请求

   ### 已知事实
   - 当前需要修改的文件：[文件路径]
   - 该文件在围栏中标记为：❌禁止修改
   - 需要修改的原因：[具体技术原因]
   - 影响范围：[说明对其他模块的影响]

   ### 待决策内容
   是否授权突破围栏，允许修改该文件？

   ### 影响
   - 如果授权：将记录突破原因并继续实现
   - 如果不授权：需要寻找替代实现方案
   ```

4. **恢复后处理**：
   - 先记录用户的回答
   - 如果获得授权：
     - 记录突破原因到 implementation-summary.md
     - 继续实现
   - 如果未获得授权：
     - 寻找替代实现方案
     - 必要时标记 `owner=design` 触发设计回流

### 4. 继续实现
4. 实现满足设计契约和任务完成条件的最小变更；
5. 运行与本次编辑直接相关的编译、静态检查或快速检查；
6. 更新任务映射、实际变更和验证证据；
7. 逐个完成剩余任务，保持接口、迁移、兼容和回滚顺序；
8. 在 implementation-summary.md 中记录所有变更与围栏的符合情况。

实现优先复用现有模块、错误处理、配置和数据模式。新增文件或抽象记录其设计锚点和必要性。生产代码、运行配置、迁移与正式文档由 task 围栏授权；基线测试文件与断言保持原内容 hash，测试资产修订通过 DT 回流重新建立基线。

当实现发现测试资产与正式契约不一致时，在摘要中记录 `owner=dt`、证据和影响；当实现路径要求改变正式契约或围栏时记录 `owner=design`。对应职责在状态回流后修订。

## 产物契约

`implementation-summary.md` 使用：

```yaml
---
ar_id: <AR-ID>
run_id: <runId>
artifact: implementation-summary
status: draft | blocked | ready
design_version: <design.md updated_at>
task_version: <task.md updated_at>
dt_quality_version: <dt-quality-review.md updated_at>
updated_at: <ISO-8601>
---
```

正文包含任务完成矩阵、Changed Files、关键实现决策、迁移/兼容/回滚处理、快速检查命令与结果、未决问题和下一步 DT 执行清单。所有 task 已完成且变更可交给实现后 DT 执行时设置为 `ready`。
